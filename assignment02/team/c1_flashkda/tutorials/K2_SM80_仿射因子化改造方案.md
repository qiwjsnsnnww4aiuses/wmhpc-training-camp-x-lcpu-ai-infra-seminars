# FlashKDA K2：SM80 仿射因子化改造方案

> 目标：把 K2 的状态递推明确改写为 `S_i = A_i S_(i-1) + B_i`，尽量把与输入状态无关的工作移到 chunk-parallel 的 K1，同时继续使用原版 SM80 `mma.sync.m16n8k16`。
>
> 本文件是实施方案，不表示代码已经修改或性能已经提升。

> **范围提醒：**本文件的 P/W 方案只缩短 K2 单个 chunk 的工作，不能让同一状态链的多个 chunk 并行。若目标是创造 chunk 间并行，请使用
> [`K2_SM80_chunk间并行_分段扫描方案.md`](./K2_SM80_chunk间并行_分段扫描方案.md)。

---

## 架构边界：这里的“仍然是 SM80”指什么

本方案中的“SM80”指矩阵乘 atom 继续使用：

```text
SM80_16x8x16_F32BF16BF16F32_TN
```

也就是仍然生成 SM80 风格的 `mma.sync` / `HMMA.16816`，不换 WGMMA 或 tcgen05。

但原版 FlashKDA 的 global-memory 到 shared-memory 搬运已经使用：

```text
SM90_TMA_LOAD
SM90_TMA_STORE
PipelineTmaAsync
```

所以本方案保留的是原项目现有组合：

```text
数据搬运：SM90 TMA
矩阵计算：SM80 MMA
运行平台：GB200/B300 等支持该二进制的目标卡
```

如果要求代码必须运行在真实 A100 / compute capability 8.0 上，则需要把 TMA pipeline 另行改成 `cp.async` 或普通 global/shared copy；那是独立的移植任务，不属于本文这次 K2 仿射因子化改造。

## 0. 最重要的结论

数学上，每个 chunk 确实可以写成：

```text
S_i = A_i S_(i-1) + B_i
```

但不应该让 K1 真的生成完整的：

```text
A_i[D,D]
B_i[D,D]
```

推荐做法是让 K1 生成 A/B 的低秩因子：

```text
P_i = R_i Kd_i
W_i = R_i V_i

R_i = INV_i diag(beta_i)
```

然后 K2 执行：

```text
X_i = P_i S_(i-1)
U_i = W_i - X_i

O_i = Qd_i S_(i-1) + Mqk_i U_i
S_i = G_i S_(i-1) + Kr_i^T U_i
```

其中：

- `Kd = k_decayed`；
- `Qd = q_decayed`；
- `Kr = k_restored`；
- `G = diag(g_total)`；
- `beta_i` 表示 sigmoid 激活后的 token beta；
- `C=CHUNK=16`，`D=128`。

因此：

```text
A_i = G_i - Kr_i^T P_i
B_i = Kr_i^T W_i
```

但 A/B 不被物化。K2 通过 `P、W、Kr、G` 隐式应用它们。

这是本方案的核心：

> 保留 `A S + B` 的数学意义，保留低秩 `C=16` 结构，避免完整 D×D 矩阵的 global-memory 和 D³ 计算灾难。

## 1. 原版 K2 当前在做什么

对一个 chunk，原版 K2 的关键计算可以概括为：

```text
KS  = Kd @ S_prev
QS  = Qd @ S_prev

E   = (V - KS) * sigmoid(beta)
U   = INV @ E

O   = QS + Mqk @ U
S   = G * S_prev + Kr^T @ U
```

形状为：

```text
S_prev, S : [D,D]   = [128,128]
Kd, Qd, Kr: [C,D]   = [16,128]
V, U, O   : [C,D]   = [16,128]
INV, Mqk  : [C,C]   = [16,16]
G         : [D]
beta      : [C]
```

原版 K1 已经处理并写入 workspace：

```text
Kd, Qd, Kr, G, INV, Mqk
```

原版 K2 另外从输入 global memory 读取：

```text
V, beta
```

K2 中真正依赖 `S_prev` 的只有：

```text
Kd @ S_prev
Qd @ S_prev
Kr^T @ U
```

`INV`、`beta`、`V`、`Kd` 都是当前 chunk 已知量，所以可以先做部分代数展开。

## 2. 从原式推导紧凑仿射形式

令：

```text
D_beta = diag(sigmoid(beta))
R      = INV @ D_beta
```

原来的 U 为：

```text
U = INV @ [D_beta @ (V - Kd @ S_prev)]
```

利用分配律：

```text
U = INV @ D_beta @ V - INV @ D_beta @ Kd @ S_prev
```

定义 K1 可以预计算的两个紧凑因子：

```text
W = R @ V       # [16,16] @ [16,128] -> [16,128]
P = R @ Kd      # [16,16] @ [16,128] -> [16,128]
```

于是 K2 中：

```text
U = W - P @ S_prev
```

代入状态更新：

```text
S = G*S_prev + Kr^T @ (W - P@S_prev)

  = (G - Kr^T@P) @ S_prev + Kr^T@W
```

因此数学上的 A/B 为：

```text
A = G - Kr^T @ P       # [D,D]
B = Kr^T @ W           # [D,D]
```

注意：`G*S_prev` 在源码里按 `g_total[D]` 对状态的对应维度缩放。这里用 `G=diag(g_total)` 表示该线性算子，不要求代码真的构造对角矩阵。

## 3. 为什么不能直接存完整 A/B

### 3.1 global memory 容量

每个 chunk、每个 head 的完整 A/B，如果用 bf16：

```text
A: 128*128*2 = 32768 bytes
B: 128*128*2 = 32768 bytes
合计          = 65536 bytes/tile
```

原版 workspace 每 tile：

```text
3 * C*D*2       = 12288 bytes   # Kd/Qd/Kr
D*4             =   512 bytes   # g_total
2 * C*C*2       =  1024 bytes   # INV/Mqk
合计            = 13824 bytes
```

完整 A/B 单独就已经是原 workspace 的：

```text
65536 / 13824 = 4.74x
```

对 fixed `T=8192, H=96`：

```text
tiles = (8192/16)*96 = 49152
A+B workspace = 49152*65536 bytes = 3.00 GiB
```

这还没有包含 output 所需的 Q/Mqk 系数、tile prefix 和对齐空间。

### 3.2 K2 计算量

如果显式存 A，再执行：

```text
A[D,D] @ S[D,D]
```

每 chunk 的计算量为：

```text
2*D^3 = 2*128^3 = 4,194,304 FLOP
```

当前因子化状态更新的两次主要乘法为：

```text
Kd[C,D] @ S[D,D]      : 2*C*D^2 = 524,288 FLOP
Kr^T[D,C] @ U[C,D]    : 2*C*D^2 = 524,288 FLOP
合计                                  1,048,576 FLOP
```

显式 `A@S` 约为当前状态相关矩阵乘的 4 倍，而且 K1 构造 A/B 本身也要计算。

### 3.3 shared memory

完整 A 或 B 的一个 bf16 tile 是 32 KiB。K2 还需要：

- 32 KiB bf16 state；
- 多级 input pipeline；
- output stages；
- barrier 和对齐空间。

如果同时缓存 A/B，会迅速推高每 CTA shared memory，进一步压低原本就只有约 9.4% 的 fixed K2 occupancy。

### 3.4 若想用 prefix scan

仿射变换的组合规则确实是：

```text
(A2,B2) o (A1,B1)
    = (A2*A1, A2*B1+B2)
```

理论上可以对 chunk 做并行 prefix scan。但每个 combine 至少包含 D×D GEMM：

```text
A2*A1
A2*B1
```

对于 D=128，这会产生大量 D³ 计算、A/B global traffic 和 scan 同步。当前 `C=16` 的低秩优势也会随着多个 chunk 组合逐渐丢失。因此不建议把它作为第一版实现。

## 4. 推荐方案：K1 预计算 P/W，K2 隐式应用 A/B

### 4.1 新的数据边界

原版：

```text
K1 -> workspace: Kd, Qd, Kr, G, INV, Mqk
K2 direct input: V, beta
```

改版：

```text
K1 -> workspace: P, W, Qd, Kr, G, Mqk
K2 direct input: 不再需要 V、beta
```

其中：

```text
R = INV @ diag(sigmoid(beta))
P = R @ Kd
W = R @ V
```

### 4.2 新 K2

```text
PS = P @ S_prev
QS = Qd @ S_prev

U  = W - PS

O  = QS + Mqk @ U
S  = G*S_prev + Kr^T @ U
```

仍然使用：

```text
SM80_16x8x16_F32BF16BF16F32_TN
```

没有改变：

- `CHUNK=16`；
- KDA 数学语义；
- K1/K2 的 kernel 数量；
- K2 的 chunk 顺序；
- K2 grid `(N,H)`；
- state 的 bf16 存储策略；
- output/final_state API。

### 4.3 预期收益与代价

K2 删除：

```text
sigmoid(beta)
逐元素 (V-KS)*beta
INV[16,16] @ E[16,128]
```

其中被移除的 K2 GEMM 为：

```text
2*C*C*D = 2*16*16*128 = 65,536 FLOP/chunk/head
```

原版 K2 的主要 tensor FLOP 约为：

```text
kS + qS       = 1,048,576
INV@E         =    65,536
Mqk@U         =    65,536
Kr^T@U        =   524,288
合计          = 1,703,936
```

改版 K2：

```text
PS + qS       = 1,048,576
Mqk@U         =    65,536
Kr^T@U        =   524,288
合计          = 1,638,400
```

K2 tensor FLOP 下降：

```text
65,536 / 1,703,936 = 3.85%
```

但 K1 新增两次 `16×16 @ 16×128`：

```text
P = R@Kd
W = R@V
```

也就是 K1 增加 131,072 FLOP，而 K2 只删除 65,536 FLOP。完整 forward 的总计算量会略增，但增加的计算放在拥有 49,152 个 CTA、occupancy 约 96.6% 的 K1；减少的计算位于 fixed 场景只有 96 个 CTA 的串行 K2。

所以本方案的研究假设不是“总 FLOP 更少”，而是：

> 用少量额外总工作，换取 K2 关键路径缩短。

理论预期应保守：K2 tensor 工作只减少约 3.85%，端到端收益很可能只有几个百分点，也可能被 workspace 流量和数值重排抵消。

## 5. Global memory 设计

### 5.1 新 workspace 布局

建议保持 separated arrays，避免大范围修改现有 TMA 逻辑：

```text
workspace
├── ws_p   [H*total_tiles, C, D] bf16
├── ws_w   [H*total_tiles, C, D] bf16
├── ws_qd  [H*total_tiles, C, D] bf16
├── ws_kr  [H*total_tiles, C, D] bf16
├── ws_gt  [H*total_tiles, D]    fp32
├── ws_mqk [H*total_tiles, C, C] bf16
└── tile_prefix [N+1] int32，128B 对齐
```

新的 per-tile workspace：

```text
4*C*D*2 + D*4 + C*C*2
= 4*16*128*2 + 128*4 + 16*16*2
= 17,408 bytes
```

与原版比较：

```text
原版 13,824 bytes/tile
改版 17,408 bytes/tile
增加 3,584 bytes/tile
增加约 25.93%
```

fixed `T=8192,H=96`：

```text
原版 workspace 主体约 648 MiB
改版 workspace 主体约 816 MiB
增加约 168 MiB
```

这里采用 `49152 tiles` 计算，未计很小的 prefix 尾部。

### 5.2 K2 每 stage 的 global read

原版近似：

```text
V              4096
beta             64
Kd/Qd/Kr       12288
G                512
INV/Mqk         1024
合计           17984 bytes/stage
```

改版：

```text
P/W/Qd/Kr      16384
G                512
Mqk              512
合计           17408 bytes/stage
```

K2 每 stage 少约 576 bytes，约 3.2%。但 K1 需要额外读取 V，并把更多中间量写入 workspace，因此完整 forward 的总 global traffic 不是下降，而是上升。

### 5.3 总 global traffic 的方向

忽略 state/output 和少量元数据，只看这次变动：

```text
原版：
K1 inputs + K1 workspace store + K2 inputs/workspace load
约 44,672 bytes/tile

改版：
K1 多读 V + 写新 workspace + K2 读新 workspace
约 51,776 bytes/tile

增加约 7,104 bytes/tile，约 15.9%
```

因此必须实测。方案只可能通过缩短低并行度 K2 的关键路径获益，不会通过减少总 global bytes 获益。

### 5.4 对齐要求

所有新数组继续保持 128-byte 对齐：

```text
C*D*sizeof(bf16) = 16*128*2 = 4096 bytes
```

4096 是 128 的整数倍，可以直接复用 `TMAVOLayout` 和现有 TMA store/load 组织。

## 6. Shared memory 设计

### 6.1 K1 shared memory

K1 当前使用 union 复用两个生命周期：

```text
Phase A: q, k, g
Phase B: Kd, Qd, k_inv, L, INV, Mqk
```

新增 P/W 后推荐的第一版 shared 布局：

```text
原有 Phase B：
Kd, Qd, k_inv, L, INV, Mqk

原有独立区：
Kr, beta, g_total

新增独立区：
V [C,D] bf16 = 4096 bytes
```

计算后的缓冲复用：

```text
k_inv 在 L/Mqk 构造后已经死亡
    -> 复用为 P 输出 [C,D]

Kd 在 P=R@Kd 完成后已经死亡
    -> 复用为 W 输出 [C,D]

INV 原地按列乘 beta
    -> 复用为 R [C,C]
```

因此只需新增一个 V tile 的峰值 shared memory，约 4 KiB。

根据原 NCU：

```text
K1 dynamic shared/CTA = 21.25 KiB
```

第一版预计增至约 25.25 KiB，仍远低于 K2 的 98.43 KiB。但必须重新用 NCU 查看 K1 theoretical/achieved occupancy，不能只靠估计。

### 6.2 为什么第一版不做极限 union

可以在 INV 生成后再发一次 TMA，把 V 搬进已经死亡的 shared 区域，从而避免新增 4 KiB。但这会引入：

- 第二个 TMA barrier 生命周期；
- async proxy fence；
- 等待和 buffer 覆盖证明；
- 更复杂的 tail 处理。

第一版应该优先保证数学和布局正确，直接增加一个 V buffer。若 benchmark 显示 K1 shared memory 导致 occupancy 下降，再做二阶段 TMA/union 优化。

### 6.3 K1 的 SM80 MMA 分工

`R[16,16] @ Kd[16,128]` 和 `R @ V` 都天然适合 SM80 `m16n8k16`。

建议 8 个 warp 分别负责一个 16 列块：

```text
warp 0 -> columns   0:16
warp 1 -> columns  16:32
...
warp 7 -> columns 112:128
```

执行顺序：

```text
所有 8 warp：P = R @ Kd
__syncthreads()
所有 8 warp：W = R @ V
__syncthreads()
TMA store P/W/Qd/Kr/G/Mqk
```

可以复用 `utils.cuh` 中 `mma_m16n16_bf16bf16bf16_1warp` 的思路，对每个 warp 传入一个 `16×16` 的 B/output local tile。第一版不需要引入 WGMMA 或 tcgen05。

### 6.4 tail 与 varlen 安全

对最后不足 16 token 的 chunk：

1. K1 当前已经将 K 的 tail rows 清零；
2. 新增 V 后，也必须将 V 的 tail rows 清零；
3. 构造 `R=INV*diag(beta)` 时，对 `j>=actual_len` 的 beta 列强制为 0；
4. 不能让 TMA 从下一条 packed sequence 读到的 V/beta 参与 P/W；
5. 正确性测试必须保留 `[17,31,16]`，并额外加入长度 1、15、16、17。

这一步是 varlen 最容易出现“fixed 正确、varlen 错误”的地方。

### 6.5 K2 shared memory

原版每个 input stage 包含：

```text
V, beta, Kd, Qd, Kr, G, INV, Mqk
```

改版每 stage 包含：

```text
P, W, Qd, Kr, G, Mqk
```

对应变化：

```text
删除 V       4096 bytes
删除 beta      64 bytes
删除 Kd      4096 bytes
删除 INV      512 bytes
新增 P       4096 bytes
新增 W       4096 bytes
净减少        576 bytes/stage
```

当前为 3 个 input stages，预计 shared memory 总共下降约：

```text
3*576 = 1728 bytes
```

原 K2 dynamic shared 为 98.43 KiB，改版预计约 96.7 KiB。下降不大，可能不会改变每 SM 可驻留 CTA 数，但应检查 Launch Statistics。

## 7. K2 计算流水如何修改

原 K2 Phase 1 已融合计算 `Kd@S` 和 `Qd@S`。推荐保留这套寄存器/双 GEMM 结构，只做输入替换：

```text
原：Kd @ S -> u_acc
新：P  @ S -> u_acc

Qd @ S -> out_acc    # 不变
```

原 Phase 2/3：

```text
加载 V、INV、beta
U0 = (V - Kd@S) * beta
U  = INV @ U0
```

改为：

```text
加载 W
PS_bf16 = cast(P@S)
U_bf16  = W - PS_bf16
```

之后保持：

```text
Mqk @ U + QS        # output
Kr^T @ U + G*S      # state update
```

需要特别保护原版的寄存器通路：

- `U` 仍应留在 registers；
- 继续使用 `SM75_U32x1_MOVM_T` 将 U 改排为 B fragment；
- 不要为了代码简单把 U 写回 shared 再读出；
- 保留 Phase 1 的 Kd/Qd 双 GEMM，只将 Kd fragment 改成 P fragment；
- 删除 INV GEMM 后，重新检查 register lifetime，避免编译器因变量生命周期变化产生 spill。

## 9. 数值正确性风险

数学上：

```text
R @ (V - Kd@S) = R@V - (R@Kd)@S
```

但有限精度中不保证逐 bit 相同，因为结合顺序和 bf16 舍入点改变：

原版：

```text
KS(fp32 acc) -> bf16
(V-KS)*beta  -> bf16
INV@...      -> fp32 acc -> bf16 U
```

改版：

```text
P=R@Kd -> fp32 acc -> bf16 workspace
W=R@V  -> fp32 acc -> bf16 workspace
PS      -> fp32 acc -> bf16
U=W-PS  -> bf16
```

主要风险：

- `R@V - (R@Kd)@S` 有额外的中间 bf16 舍入；
- 两项接近时相减可能产生 cancellation；
- 误差会沿 512 个 chunk 的状态链累积；
- gate 接近 0 时旧状态保留较强，更容易积累；
- 极端 beta 或大初始 state 可能放大差异。

因此第一版验收不能要求逐 bit 等于原版，但应同时报告：

```text
max_abs
mean_abs
rel_rmse
cosine similarity
NaN/Inf
误差随 chunk 的曲线
```

建议先用以下门槛拦截布局错误：

```text
output rel_rmse < 0.01
state  rel_rmse < 0.01
无 NaN/Inf
```

这只是开发门槛，不应自动成为最终精度标准。最终标准需要与原版、naive 和模型容忍度共同决定。

## 10. 分阶段实施顺序

### 阶段 0：建立不可变基线

保存同一环境下的：

```text
官方 tests
fixed / varlen benchmark
K1 / K2 分 kernel NCU
原版 SASS 中 HMMA 数量
```

不要用之前不同 harness 的延迟作为唯一基线。原版和改版必须在同一个脚本中成对计时。

### 阶段 1：仅实现数学因子，先用普通 CUDA 验证

在小规模测试或 debug kernel 中计算：

```text
R = INV*diag(beta)
P = R@Kd
W = R@V
U_new = W-P@S
U_old = INV@((V-Kd@S)*beta)
```

比较 U、output、state。此阶段用于确认矩阵方向、beta 是缩放 R 的列而不是行，以及 state 的转置布局。

### 阶段 2：K1 用 SM80 MMA 生成 P/W

先只修改 K1 和 workspace，并写一个调试脚本把 P/W 从 workspace 导出，与 PyTorch 参考对拍。此时可以暂时不接 K2。

验收：

```text
P/W shape 正确
fixed 与 varlen tail 正确
P/W rel_rmse 达到预期
cuda-memcheck/compute-sanitizer 无 OOB
```

### 阶段 3：接入 K2

将 K2 的 `Kd@S + INV` 路径替换成 `P@S` 和 `W-P@S`，保留后续 Mqk/output/state update。

先测试：

```text
T = 1, 15, 16, 17, 31, 64
H = 1, 2
zero initial state / random initial state
fixed / varlen
```

之后再跑 T=8192、H=96。

### 阶段 4：性能与资源

用相同输入成对测量：

```text
原版完整 fwd
改版完整 fwd
原版 K1 / K2
改版 K1 / K2
```

必须分 kernel 看，否则可能出现 K2 快 3%、K1 慢 10%，完整 forward 反而退化。

### 阶段 5：第二轮 shared 优化

只有第一版正确且 profile 表明 K1 shared 增长是瓶颈时，再考虑：

- INV 后二次 TMA load V；
- 用死亡的 Phase A/B 缓冲承载 V；
- P TMA store 完成后复用其 shared buffer；
- 减少 pipeline stage 或改变 store 顺序。

不要在第一版同时做代数变换、布局重写和极限 shared 复用，否则错误很难定位。

核心形状：

- 没有意外变成标量 FMA 主导；
- ptxas register/spill 没有明显恶化。

## 12. 可选的第二级方案：进一步预计算 output 仿射因子

还可以在 K1 继续计算：

```text
Qhat = Qd - Mqk@P
Ohat = Mqk@W
```

使 K2 output 变成：

```text
O = Qhat@S + Ohat
```

同时 state 仍为：

```text
U = W-P@S
S = G*S + Kr^T@U
```

优点：K2 再删除一个 `Mqk@U` 小 GEMM。

缺点：

- K1 再增加两个小 GEMM；
- workspace 需要 P/W/Qhat/Ohat/Kr，共 5 个 C×D tile；
- per tile 境长到约 20,992 bytes；
- K2 每 stage 读量也上升；
- K2 shared 可能增加，进一步压 occupancy；
- 数值重排更多。

所以它只适合作为第二个实验点，不建议与第一版同时实现。

---

## 13. 不建议的方案：K1 直接输出 B=Kr^T W

看起来 B 与旧状态无关，可以让 K1 直接输出：

```text
B[D,D] = Kr^T[D,C] @ W[C,D]
```

但 K2 仍要计算状态相关项：

```text
-Kr^T @ (P@S)
```

原版只需一次：

```text
Kr^T @ (W-P@S)
```

预计算 B 后，K2 的 D×C×D GEMM 并没有消失，反而新增一个 32 KiB/tile 的 B workspace、一次 K1 GEMM 和一次 K2 D×D 加法。因此不推荐。

## 14. 成功与停止条件

### 可以继续优化

满足：

```text
正确性通过
长序列误差可接受
K2 latency 明显下降
K1 occupancy 没有明显恶化
完整 forward 至少不退化
```

再尝试 V buffer 的二次 TMA/union 复用、output 仿射因子或 persistent 调度。

### 应停止该路线

出现任一情况：

```text
长序列 state 误差持续放大
K1 增加的工作超过 K2 节省
workspace/global traffic 成为新瓶颈
K2 仍主要受 no-eligible/状态链限制，删除小 GEMM 几乎无收益
H=12 等真实部署形状明显退化
```

这时结论应是：`A S+B` 的数学抽象正确，但显式或半显式物化不适合当前低秩 KDA 实现。下一步应研究调度并行度，而不是继续扩大 workspace。

---

## 15. 最终推荐

第一版只实现以下范围：

```text
K1:
    R = INV*diag(beta)
    P = R@Kd
    W = R@V
    store P,W,Qd,Kr,G,Mqk

K2:
    PS = P@S
    QS = Qd@S
    U  = W-PS
    O  = QS+Mqk@U
    S  = G*S+Kr^T@U
```

理由：

1. 数学上完整体现 `S_i=A_iS_(i-1)+B_i`；
2. 不物化 A/B，保留 CHUNK=16 的低秩计算优势；
3. P/W 都是 `16×16 @ 16×128`，与 SM80 m16 tile 匹配；
4. K2 删除一次小 GEMM和 beta 路径，改动边界清晰；
5. K2 input-stage shared 略降；
6. 虽然 workspace 增约 25.9%、总流量增加，但这是一个可量化、可回滚、能验证“把工作移出串行 K2 是否有价值”的实验。

对性能必须保持保守预期：

> 该方案更像是一次“关键路径搬移实验”，不是预期大幅加速的方案。若完整 forward 能稳定提升 2%～5%，已经说明方向有价值；若持平或退化，也能证明 fixed K2 的主要问题并非那一次 INV 小 GEMM，而是状态依赖和整体并行度。
