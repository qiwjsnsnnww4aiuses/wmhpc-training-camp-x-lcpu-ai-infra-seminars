### 1.1 从 Python 到 GPU 的文件地图

先把“源码文件”、“Python 包”和“编译后的动态库”分开。完整上游目录的
关键结构是：

```text
FlashKDA-upstream/
├── setup.py                         # 告诉 PyTorch 如何编译 CUDA extension
├── flash_kda/
│   └── __init__.py                  # 面向用户的 Python wrapper
├── csrc/
│   ├── flash_kda.cpp                # PyBind 入口、参数检查和 dispatch
│   ├── fwd.h                        # launch_fwd 的 C++ 声明
│   └── smxx/
│       ├── utils.cuh                # MMA helper、pipeline、工作区和精度转换
│       ├── fwd_kernel1.cuh          # K1 prepare kernel
│       ├── fwd_kernel2.cuh          # K2 recurrence kernel
│       └── fwd_launch.cu            # TMA descriptor、workspace 切分、K1/K2 launch
├── tests/                            # correctness 测试与参考实现
├── benchmarks/                       # 计时和 NCU 入口
└── flash_kda_C*.so                  # 编译后出现；Python 动态扩展
```

`setup.py` 的 extension 名是 `flash_kda_C`，直接编译的 translation units 只有：

```text
csrc/flash_kda.cpp
csrc/smxx/fwd_launch.cu
```

`fwd_kernel1.cuh`、`fwd_kernel2.cuh` 和 `utils.cuh` 是头文件，由
`fwd_launch.cu` 包含后一起编译，不会被 Python 分别打开执行。

`pip install -e .` 也不是让 Python 每次现场编译 CUDA。它先用
PyTorch `CUDAExtension` + nvcc 建出 `flash_kda_C*.so`，然后把 Python 包以
editable 方式指向当前源码目录。之后普通运行只需加载已编译的
`.so`。

### 1.2 `python tests/test_fwd.py` 运行时到底发生什么

是的，Python 运行测试文件时会加载动态链接库，但还要区分 CPU 端和
GPU 端：

```text
tests/test_fwd.py
  └─ import flash_kda
       └─ flash_kda/__init__.py
            ├─ import torch
            └─ from flash_kda_C import fwd as _fwd_raw
                 └─ CPython 加载 flash_kda_C*.so

test 调用 flash_kda.fwd(...)
  ├─ Python wrapper 计算 workspace 大小并分配 CUDA tensor
  └─ _fwd_raw(...)
       └─ csrc/flash_kda.cpp::fwd                  [CPU host code]
            ├─ 检查 device、dtype、shape、contiguous
            ├─ 将 [B,T,H,D] 视为 [B*T,H,D]
            ├─ 取得 PyTorch 当前 CUDA stream
            ├─ 根据 fixed/varlen、state 有无、BF16/FP32 选模板实例
            └─ launch_fwd(...)
                 └─ csrc/smxx/fwd_launch.cu       [CPU host code]
                      ├─ 切分 workspace
                      ├─ 创建 TMA descriptor
                      ├─ launch K1 prepare         [GPU kernel]
                      └─ launch K2 recurrence      [GPU kernel]
```

`.so` 里同时有：

- CPU 上执行的 PyBind/C++ host 代码；
- 链接到 PyTorch 的 `libc10.so` 等动态库的依赖；
- nvcc/ptxas 生成的 GPU code object（cubin/fatbin）。

CPU 端 `launch_fwd` 不是自己完成 KDA 数学计算，而是把 K1/K2 提交到
PyTorch 当前 CUDA stream。CUDA launch 是异步的：Python 线程可以在 GPU
完成前返回；correctness 中的 `torch.cuda.synchronize()` 和 benchmark 中的
CUDA event/synchronize 才负责等待和测量。

### 1.3 `csrc/smxx/` 四个文件的分工

`smxx` 是这份代码的共享 CUDA 实现目录，而不是“已经使用 SM100
tcgen05”的意思。它同时混合了：

- SM90 TMA/pipeline：负责供数和异步流水；
- SM80 warp-level MMA atom：负责主要矩阵乘；
- 针对 `sm_90a/sm_100a/sm_103a/sm_120a` 编译的 code object。

“目标 code object 是 `sm_103a`”不代表编译器会自动把源码里的
SM80 MMA atom 换成 tcgen05。这正是本题要用源码 + SASS + NCU 验证的
地方。

#### `utils.cuh`：共用底层积木

这个文件主要包含：

- `WorkspaceSizes`：每个 tile 的工作区字节布局；
- load/store pipeline 的角色和初始化；
- `mma_m16n16_*_1warp`：用两个 `m16n8k16` atom 组成 16×16；
- `neumann_inv_fused_1warp`：在寄存器中用 MMA 完成 16×16 Neumann 级数；
- FP32 state ↔ BF16 state 的 shared-memory 转换 helper。

它显式包含 `cute/arch/mma_sm80.hpp`，并使用：

```text
SM80_16x8x16_F32BF16BF16F32_TN
SM80_16x8x16_F16F16F16F16_TN
```

#### `fwd_kernel1.cuh`：K1 prepare

K1 的并行单位是“一个 head 的一个 16-token tile”，grid 为：

```text
(total_tiles, H)
```

它的主要流程是：

1. fixed 直接定位 tile；varlen 利用 tile-prefix 定位所属序列；
2. 用 TMA 把 `q/k/g/beta/dt_bias` 搬入 shared memory；
3. 激活 gate，计算 chunk 内累积衰减；
4. 得到 `k_decayed/q_decayed/k_restored/g_total`；
5. 用 SM80 MMA helper 计算 16×16 的 `L` 和 `Mqk`；
6. 用 Neumann 级数得到 `INV`；
7. 把 K2 需要的六组中间量写全局 workspace。

K1 输出的 workspace 内容是：

```text
k_decayed, q_decayed, k_restored, g_total, INV, Mqk
```

各 tile 之间的 K1 几乎没有递推依赖，因此可以大规模并行。

#### `fwd_kernel2.cuh`：K2 recurrence

K2 的并行单位是“一条 sequence 的一个 head”，grid 为：

```text
(N, H)
```

每个 CTA 内部再按时间顺序遍历这条序列的 chunk，因为下一个 chunk
要使用上一个 chunk 的 state。这就是 fixed H96 只有 96 CTA，而
varlen `N=8` 可有 768 CTA 的根本原因。

K2 采用 warp specialization：

- 4 个 MMA warp 负责 Tensor Core 计算；
- 1 个 load warp 发起 TMA load；
- 1 个 store warp 写回 output/state。

主要计算可以概括为：

```text
读取当前 state S
  → 计算 k @ S 和 q @ S
  → 根据 v、beta 得到更新量
  → U = INV @ update
  → output = q @ S + Mqk @ U
  → state = decay(state) + k_restored^T @ U
  → 进入下一个 chunk
```

FP32 boundary state 也在这里处理：入口 FP32 先转 BF16，内部递推使用
BF16 state，出口再转回 FP32。

#### `fwd_launch.cu`：host launch 和供数布局

这个文件本身主要在 CPU 端做 launch 准备：

1. 将 Python wrapper 分配的一整块 workspace 切成六组 tensor；
2. 为 q/k/v/g/beta/workspace/state/out 创建 TMA descriptor；
3. 选择 BF16/FP32 state 的 TMA layout；
4. 先 launch `_flash_kda_fwd_prepare`；
5. 后 launch `_flash_kda_fwd_recurrence`；
6. 显式实例化 fixed/varlen 和各种 state 组合。

这里使用 `SM90_TMA_LOAD/STORE`，只说明搬运路径用了 TMA；主要
矩阵乘用什么指令要继续看 `MMA_Atom` 和最终 SASS。

#### `flash_kda.cpp`：Python/CUDA 之间的桥

这个文件不在 `smxx/` 里，但它是理解调用链必须的入口：

- `PYBIND11_MODULE` 把 C++ `fwd` 暴露成 Python 的 `flash_kda_C.fwd`；
- 检查 tensor 是否在 CUDA、是否 contiguous、dtype/shape 是否正确；
- 根据 `cu_seqlens` 有无选 fixed/varlen；
- 根据 initial/final state 有无及 dtype 选择编译好的模板实例；
- 将 tensor 的 device pointer 和当前 CUDA stream 传给 `launch_fwd`。

`repro_results` 不是 FlashKDA 的输入，kernel 也不会读它。这是本指南约定的

```text
../repro_results/tests/test_fwd_direct.log
```

其中 `..` 是回到上一级 `c1_flashkda/`，所以文件最终位于：

```text
c1_flashkda/repro_results/tests/test_fwd_direct.log
```

以下命令：

```bash
python tests/test_fwd.py \
  2>&1 | tee ../repro_results/tests/test_fwd_direct.log
```

等价于单行：

```bash
python tests/test_fwd.py 2>&1 | tee ../repro_results/tests/test_fwd_direct.log
```

各部分含义：

- `python tests/test_fwd.py`：用当前激活环境的 Python 执行测试；
- 行末 `\`：Bash 续行，下一行仍属于同一条命令；
- `1`：标准输出 stdout；`2`：标准错误 stderr；
- `2>&1`：把 warning/error 通道合并到普通输出；
- `|`：将左边的输出流传给右边；
- `tee file`：同时显示在终端并覆盖写入 `file`；需要追加才用 `tee -a`。

`tee` 只复制文本输出，不参与 KDA 计算。`set -o pipefail` 则让整条
pipeline 在 Python 失败时仍返回失败，避免 `tee` 成功写日志后把前面的
错误伪装成成功。

建议用 `script` 保存完整终端会话：

```bash
script -a repro_results/reproduce_terminal.log
```

之后所有命令和输出都会记录。结束时运行：

```bash
exit
```

这条 `exit` 是结束 `script` 记录，不是删除环境。

为了让带 `tee` 的命令在 Python 失败时仍返回失败状态，当前 Bash 会话执行：

```bash
set -o pipefail
```

## 12. 源码层先确认 SM80 MMA

源码层要回答两个问题：

1. K1/K2 从哪里选中 SM80 MMA atom？
2. 源码中是否存在 tcgen05/WGMMA 的替代计算路径？

集群节点可能没有 ripgrep (`rg`)，因此本节使用 Ubuntu 默认已有的
GNU `grep`，不需要 `sudo apt` 或 `snap install`。在完整 clone 中执行：

```bash
cd ~/lcpu2026/assignment02/team/c1_flashkda/FlashKDA-upstream
mkdir -p ../repro_results/sass

grep -RInE \
  --include='*.cu' \
  --include='*.cuh' \
  'mma_sm80|SM80_16x8x16|tcgen05|wgmma' \
  csrc/smxx \
  | tee ../repro_results/sass/source_instruction_evidence.txt
```

### 12.1 这条 `grep` 命令每一部分是什么

```text
grep                 搜索文本
-R                   递归进入 csrc/smxx 的子目录
-I                   跳过二进制文件
-n                   打印行号
-E                   启用扩展正则，模式里的 | 表示“或”
--include='*.cu'      只看 .cu
--include='*.cuh'     只看 .cuh
'A|B|C'              匹配 A、B 或 C；引号防止 shell 把里面的 | 当管道
csrc/smxx            搜索起点
| tee file           显示结果，并存成证据文件
```

注意命令里有两种看起来相同的 `|`：

- `'A|B'` 引号里的 `|` 是 grep 正则的“或”；
- `csrc/smxx | tee ...` 引号外的 `|` 是 Bash pipeline。

行末 `\` 只是 Bash 续行符，不是 grep 参数。多行命令与写成单行完全等价。

预期看到：

```text
include <cute/arch/mma_sm80.hpp>
SM80_16x8x16_F32BF16BF16F32_TN
SM80_16x8x16_F16F16F16F16_TN
```

如果合并输出里只有 SM80 行，没有 tcgen05/WGMMA，说明该目录没有写出
对应的备选路径。可以单独把“无命中”保存成证据：

```bash
if grep -RInEi \
  --include='*.cu' \
  --include='*.cuh' \
  'tcgen05|wgmma' \
  csrc/smxx \
  > ../repro_results/sass/source_sm100_hits.txt
then
  cat ../repro_results/sass/source_sm100_hits.txt
else
  echo 'No tcgen05/wgmma source hits under csrc/smxx' \
    | tee ../repro_results/sass/source_sm100_hits.txt
fi
```

grep 没找到文本时返回状态 1，这在“搜索不存在的指令”时是正常
结果，不是 shell 损坏。这个 `if ... else` 将它转成一行明确证据。

### 12.2 分别追到 K1 和 K2

K1 不在每个调用点重写 `SM80_...`，它调用 `utils.cuh` 里的封装：

```bash
grep -nE \
  'mma_m16n16|neumann_inv' \
  csrc/smxx/fwd_kernel1.cuh \
  | tee ../repro_results/sass/k1_mma_calls.txt
```

应看到 `mma_m16n16_bf16bf16fp16_1warp`、
`mma_m16n16_bf16bf16bf16_1warp` 和 `neumann_inv_fused_1warp`。

K2 直接建立 MMA atom，再把它传给多个 `gemm` 调用：

```bash
grep -nE \
  'MMA_Atom|SM80_16x8x16|gemm\(' \
  csrc/smxx/fwd_kernel2.cuh \
  | tee ../repro_results/sass/k2_mma_calls.txt
```

调用链是：

```text
K1 fwd_kernel1.cuh
  → mma_m16n16_* / neumann_inv_fused_1warp
  → utils.cuh
  → SM80_16x8x16 atom

K2 fwd_kernel2.cuh
  → MMA_Atom<SM80_16x8x16...>
  → cute::gemm(...)
```

主要位置：

- `csrc/smxx/utils.cuh`：16×16 MMA helper 与 Neumann inverse；
- `csrc/smxx/fwd_kernel1.cuh`：调用 helper 的 K1 数学步骤；
- `csrc/smxx/fwd_kernel2.cuh`：K2 fused MMA；
- include 使用 `cute/arch/mma_sm80.hpp`。

源码证据说明作者明确选择了 SM80 warp-level MMA atom，但题目还要求确认实际 B300 二进制，因此继续做 SASS。

## 13. 导出和检查 SASS

SASS 是 NVIDIA GPU 架构实际执行的机器指令的可读反汇编形式。
CUDA/CuTe 源码先经 nvcc 生成 PTX/设备代码，再由 ptxas 生成针对
`sm_103a` 等架构的 cubin；`cuobjdump` 能从 `.so` 里取出 code object
并反汇编。

因此 SASS 可以检查“编译器最后真正放进二进制的指令”，但 SASS
仍是静态证据：整个 `.so` 中出现一条指令，不自动证明当前 benchmark
调到的 K1/K2 模板实例一定执行了它。最后还要用 NCU 关联 kernel 名、
Source 和 SASS。

### 13.1 找到 extension 路径

```bash
FLASHKDA_SO_PATH=$(python -c 'import torch; import flash_kda_C; print(flash_kda_C.__file__)')
echo "$FLASHKDA_SO_PATH" | tee ../repro_results/sass/extension_path.txt
test -f "$FLASHKDA_SO_PATH" && echo "extension exists"
```

一定要先 `import torch`。`flash_kda_C*.so` 依赖 PyTorch 的 `libc10.so`、
`libtorch.so` 等库；正常的 `import flash_kda` 会在 Python wrapper 第一行
先加载 torch。若绕过 wrapper 直接：

```bash
python -c 'import flash_kda_C'
```

可能报：

```text
ImportError: libc10.so: cannot open shared object file
```

这通常是动态库加载顺序问题，不是 CUDA extension 突然编译坏了。先用：

```bash
python -c 'import torch; import flash_kda_C; print(flash_kda_C.__file__)'
```

验证。

变量名使用 `FLASHKDA_SO_PATH`，不要覆盖系统的 `HOME`、`PATH` 等变量。

### 13.2 确认 code object

```bash
command -v cuobjdump
cuobjdump --version | tee ../repro_results/env/cuobjdump_version.txt

cuobjdump --list-elf "$FLASHKDA_SO_PATH" \
| tee ../repro_results/sass/code_objects.txt
```

检查是否包含当前 B300 的 `sm_100a` 或 `sm_103a` 目标。已实测
capability 为 `(10,3)` 且用 `FLASH_KDA_CUDA_ARCHS=auto` 编译时，应优先看到
`sm_103a`。这一步是防止分析错架构、旧环境里的 `.so`。

### 13.3 dump SASS

```bash
cuobjdump --dump-sass "$FLASHKDA_SO_PATH" \
> ../repro_results/sass/flash_kda_b300.sass

wc -l -c ../repro_results/sass/flash_kda_b300.sass \
  | tee ../repro_results/sass/sass_file_size.txt
```

`>` 表示把全部 SASS 写入文件而不在终端刷几万行；重复执行会覆盖
旧文件。`wc -l -c` 分别记录行数和字节数，用于确认导出不是空文件。

先定位 K1/K2 函数名：

```bash
grep -m 100 -nE \
  '_flash_kda_fwd_(prepare|recurrence)' \
  ../repro_results/sass/flash_kda_b300.sass \
  | tee ../repro_results/sass/kernel_locations.txt
```

因为 fixed/varlen、state 有无、BF16/FP32 state 都有不同模板实例，同一个
K1/K2 基础名出现多次是正常的。

再搜索候选 Tensor Core opcode：

```bash
grep -m 200 -niE \
  'HMMA|HGMMA|MMA|TCGEN|UTCMMA|UMMA|WGMMA' \
  ../repro_results/sass/flash_kda_b300.sass \
  | tee ../repro_results/sass/instruction_hits.txt
```

这里新增的 grep 参数是：

```text
-m 200     找到 200 行后停止，避免终端被大量 SASS 刷屏
-i         忽略大小写
-n         显示反汇编文件行号
-E         启用 A|B|C 这种备选正则
```

为什么同时搜索多个名字：PTX 指令名与最终 SASS opcode 命名不一定
完全相同，不同 CUDA/cuobjdump 版本也可能改变显示方式。不要在看到
实际输出前预设“必须叫 HMMA”。

### 13.4 你要证明的不是简单“grep 没找到”

可靠证据链应为：

1. code object 是当前 B300 架构；
2. 源码的 K1 helper 和 K2 atom 都追到 `SM80_16x8x16`；
3. disassembly 中能定位 K1/K2 kernel；
4. kernel 主体存在与 `m16n8k16` 对应的 warp MMA 指令；
5. 没有 tcgen05/UMMA 类主计算路径；
6. NCU Source/SASS 页面显示这些指令实际被执行。

仅凭整份 `.so` 中“没有字符串 tcgen05”并不充分，因为：

- SASS 命名可能不同；
- `.so` 可能包含多个架构 code object；
- 你可能没有定位正确 kernel；
- 编译器可能内联/重命名函数。

报告中只截取：

- code object 目标；
- K1/K2 名称附近；
- 几条代表性 MMA；
- 对应源文件位置。

- DRAM throughput；
- DRAM read/write bytes；
- L2 throughput；
- L2 hit rate；
- L1/SMEM throughput。

### 15.5 warp 在等什么

关注：

- long scoreboard；
- short scoreboard；
- barrier/membar；
- wait；
- not selected。

解释方式：

| 观察 | 候选解释 |
|---|---|
| DRAM 高 + long scoreboard 高 | 内存带宽/延迟 |
| Tensor 高 + DRAM不高 | 更偏 compute-bound |
| Tensor、DRAM都低 + active SM 很少 | 网格/并行度不足 |
| active SM 足 + eligible warp 低 + barrier 高 | pipeline/同步依赖 |
| occupancy 被 SMEM/register 卡住 | 资源受限 |

不要用单个 stall 百分比独立下结论。

## 17.1 `cute/tensor.hpp: No such file or directory`

```bash

```

## 17.2 `unsupported gpu architecture 'compute_...'`

原因：nvcc 太旧，或 arch 与 toolkit 不匹配。

检查：

```bash
which nvcc
nvcc --version
python -c 'import torch; print(torch.cuda.get_device_capability())'
```

解决：切到课程提供的 CUDA 12.9/13.x；不要通过删掉 arch flag 假装构建成功。

## 17.3 `FLASH_KDA_CUDA_ARCHS=auto requires a visible CUDA device`

原因：当前 Python 看不到 GPU。

检查：

```bash
nvidia-smi -L
python -c 'import torch; print(torch.cuda.is_available())'
```

优先重新取得 B300 allocation。

## 17.4 编译被杀死或非常慢

可能是编译并行度过高：

```bash
NVCC_THREADS=2 FLASH_KDA_CUDA_ARCHS=auto \
python -m pip install -v --no-build-isolation -e .
```

保留日志，确认是 host RAM OOM 还是正常模板编译耗时。

## 17.5 `ModuleNotFoundError: flash_kda_C` 或 `libc10.so` 找不到

`ModuleNotFoundError: flash_kda_C` 说明 Python wrapper 在，但 CUDA extension
没有成功安装到当前环境，或当前 Python 不是建它的那个环境。

检查：

```bash
which python
python -m pip show flash-kda
grep -nE 'error:|fatal:' ../repro_results/build/pip_install_flashkda.log
```

不要只反复执行 import；先修编译错误。

如果是：

```text
ImportError: libc10.so: cannot open shared object file
```

先确认是否绕过了正常 wrapper，并按顺序导入：

```bash
python -c 'import torch; import flash_kda_C; print(flash_kda_C.__file__)'
```

`libc10.so` 是 PyTorch 的动态库。先 import torch 后成功，就是加载顺序问题，
不需要重新编译。如果这条仍失败，再记录：

```bash
python - <<'PY'
from pathlib import Path
import torch

print("torch:", torch.__file__)
print("torch lib:", Path(torch.__file__).parent / "lib")
PY
```

不要在没有确认原因时把某个临时路径永久写入 `.bashrc`。

## 17.6 `no kernel image is available for execution on the device`

说明 code object 与实际 GPU capability 不匹配。

处理：

1. 打印 capability；
2. `cuobjdump --list-elf` 查看编译目标；
3. 清理当前项目的扩展 build cache时要先确认精确目录；

常见原因：

- 架构专用 code object 不匹配；

## 23. 讨论 1：CHUNK=16 的三个理由

### 23.1 要做的事情

1. 证明实现确实把 `CHUNK` 固定为 16；
2. 证明指数路径使用 `ex2.approx.ftz.f32`；
3. 计算 lower bound = -5 时 C=16/32/64 的最坏累计范围；
4. 量化 16/32/64 dense Neumann inverse 的每 token 代价；
5. 说明 `m16n8k16` 为什么恰好适合 C=16。

### 23.2 保存源码证据

在远程 C1 根目录执行：

```bash
cd ~/lcpu2026/assignment02/team/c1_flashkda
mkdir -p repro_results/analysis

grep -RInE \
  'constexpr int CHUNK = 16|ex2\.approx\.ftz\.f32|neumann_inv|SM80_16x8x16' \
  FlashKDA-upstream/csrc \
  | tee repro_results/analysis/q1_source_evidence.txt
```

### 23.3 保存纸面量化

```bash
python3 - <<'PY' | tee repro_results/analysis/q1_chunk_quantification.txt
import math

for c in (16, 32, 64):
    cumulative = -5 * c
    inverse_gemms = 2 * (int(math.log2(c)) - 1)
    inverse_flops_per_chunk = inverse_gemms * 2 * c**3
    print(
        f"C={c:2d}: sum_g={cumulative:4d}, "
        f"exp(sum_g)={math.exp(cumulative):.4e}, "
        f"exp(-sum_g)={math.exp(-cumulative):.4e}, "
        f"inverse_GEMMs={inverse_gemms}, "
        f"inverse_FLOP/token={inverse_flops_per_chunk // c}"
    )
PY
```

判定时不要只说“C 大了会不稳定”，而要给数字：

- C=16 最坏累计为 -80，仍在 FP32 FTZ normal 与有限值边界内；
- C=32 到 -160，正向/反向指数会下溢/上溢；
- inverse 每 token 从 3,072 FLOP 增到 16,384/81,920 FLOP，即
  5.33 倍/26.67 倍。

### 23.4 完成标准

本题主要是“源码 + 纸面量化”，不需要专门再烧一次 B300
benchmark。但必须补上一句局限：这是 worst-case bound，不代表真实
gate 平均总在 -5。

## 24. 讨论 2：tcgen05 tile 匹配与“只换指令”

## 26. 讨论 4：compute-bound 还是 memory-bound

### 26.1 这题不能只靠 SASS

SASS 只能证明有什么指令，不能告诉你 Tensor pipe/HBM/L2 到底谁在限制
延迟。因此讨论 4 必须使用 FlashKDA 本体的 K1/K2 NCU，不能用
challenge microbench 的 NCU 替代。

### 26.2 每个 kernel 要抄哪些数

| 类别 | NCU 中查看的项 |
|---|---|
| 时间 | Duration，K1/K2 各自占比 |
| 并行度 | Grid Size、Waves Per SM、Achieved Occupancy、active/eligible warps |
| 计算 | SM Throughput、Tensor pipe cycles/instructions |
| 存储 | DRAM Throughput、DRAM bytes read/write、L2 Throughput/hit rate |
| 等待 | long scoreboard、short scoreboard、barrier、not selected |
| 资源 | registers/thread、shared memory/CTA |

将 GUI/CLI 中的结果手工录入：

```text
repro_results/analysis/q4_ncu_summary.md
```

用以下规则分类：

- Tensor 高、DRAM 低、eligible warps 充足：倾向 compute-bound；
- DRAM 高且 long scoreboard 高：倾向 HBM-bound；
- L2 高而 DRAM 不高：倾向 cache/L2-bound；
- Tensor/DRAM 都低，waves/active SM 也低：是 underfill，不是“都不忙所以很快”；
- active warps 有但 eligible warps 低，barrier 高：倾向 pipeline/sync bound。

与 M4.5 的联系只能这样写：`in_proj_qkvgfab` 是 FlashKDA 前面的输入
投影 GEMM，它证明瘦 shape 会使 Tensor Core 达成率塌陷；但它和
FlashKDA K1/K2 不是同一 kernel，不能共用同一个 Roofline 数字。
