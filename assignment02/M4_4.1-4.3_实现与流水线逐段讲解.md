# M4 4.1–4.3：从一块矩阵乘法到 TMA 流水线

> 对照源码：[`01_tiled.cu`](cuda/m4_gemm/01_tiled.cu)、[`02_tma.cu`](cuda/m4_gemm/02_tma.cu)、[`03_pipeline.cu`](cuda/m4_gemm/03_pipeline.cu)。本文解释已写入的实现，不包含 4.4。**当前本地环境没有 `nvcc`/B300，以下代码经过静态检查，但尚未在目标 GPU 上得到 `PASS` 或 TFLOPS；实验栏必须由 B300 运行结果填写。**

## 0. 一分钟看完三题在改什么

三题计算同一个式子：

\[
D_{m,n}=\sum_{k=0}^{K-1}A_{m,k}B_{n,k}
\]

输入形状 `A[M,K]`、`B[N,K]`，输出 `D[M,N]`。注意这里等价于数学上的 `D=A Bᵀ`，不是把 B 当成 `[K,N]` 行主序存储。

| 版本 | GMEM → SMEM | 输入缓冲槽 | TMA 与 MMA 能否跨 tile 重叠 | 主要教学点 |
|---|---|---:|---|---|
| 4.1 | 128 个 CUDA 线程手工 load/store + swizzle | 1 | 否 | 完整 grid、K 循环、累加与覆盖同步 |
| 4.2 | TMA 硬件搬运并完成 swizzle | 1 | 基本不能 | tensor map、`full/empty` 两类完成事件 |
| 4.3 | TMA | `STAGES` 个 | 可以 | 环形缓冲、phase、所有权、预取兜底 |

它们**不是三种数学算法**。乘加和输出 tile 都相同，变化的是“下一批 A/B 怎么及时、安全地送到 Tensor Core”。

```text
                         4.1 手工                4.2 TMA              4.3 多 stage
GMEM A/B ───────────────→ CUDA线程 ───────────┐
       └──────────────────────────────────→ TMA ├─→ SMEM A/B ─→ tcgen05.mma ─→ TMEM D ─→ D
                                               ↑
                                  4.3 有多个槽，可以一边填未来，一边算当前
```

## 1. 固定形状与“一个 CTA 到底做什么”

```cpp
BM = 128; BN = 64; BK = 64;
grid = (M / BM, N / BN);
```

一个 CTA（128 个线程）认领一个 **`128×64` 输出小矩阵**。CTA 坐标 `(blockIdx.x, blockIdx.y)` 决定：

```cpp
tileM = blockIdx.x * BM;
tileN = blockIdx.y * BN;
```

这个 CTA 只写：

```text
D[tileM : tileM+128, tileN : tileN+64]
```

例如 `M=N=K=4096`：`grid=(32,64)`，共 `2048` 个 CTA。CTA `(2,3)` 计算 `D[256:384,192:256]`，不会写别的输出 tile。

K 维很长，但 SMEM 每次只放 `BK=64` 个 K 元素：

```text
iteration 0：A[..., 0:64]、B[..., 0:64]
iteration 1：A[..., 64:128]、B[..., 64:128]
iteration 2：A[..., 128:192]、B[..., 128:192]
...
```

每个 `BK=64` 又拆成四条 k16 `tcgen05.mma`。对一个 CTA 而言，**所有 K iteration 都累加到同一个 TMEM D tile**，最终只写一次 GMEM。

### 1.1 两类片上存储不要混

一个输入 stage 需要：

```text
A：128 × 64 × 2 B = 16 KiB
B： 64 × 64 × 2 B =  8 KiB
合计                    24 KiB SMEM
```

输出部分和需要：

```text
D：128 × 64 × 4 B = 32 KiB TMEM
```

`STAGES=3` 表示存三份**输入**，即 `3×24=72 KiB SMEM`；仍只计算同一份 `128×64` 输出，TMEM accumulator 仍是 `32 KiB`。像三盘待加工原料，对应一件正在完成的产品。

## 2. 4.1：手工 staging 的完整 GEMM

### 2.1 SMEM 里如何放 A/B

动态 SMEM 申请 `24 KiB + 1024 B`。`smem_raw` 不保证刚好在 1024-byte 边界，代码把使用起点向上对齐；多出的 1024 B 是最坏情况下的对齐余量。

```text
对齐后的 smem
┌───────────────────── 16 KiB ─────────────────────┬──── 8 KiB ────┐
│                    A tile                        │    B tile     │
└──────────────────────────────────────────────────┴───────────────┘
```

`swz128(row, k*2)` 把逻辑 `[row,k]` 转成 128B swizzle 的物理字节偏移。`row` 和 `k` **是当前 tile 的本地坐标**；读取 GMEM 时才加 `tileM/tileN/it*BK`：

```cpp
gA[(tileM + row) * K + it * BK + k]
gB[(tileN + row) * K + it * BK + k]
```

为什么要 swizzle？Tensor Core 按 descriptor 解读 SMEM 地址，若物理摆放与 descriptor 声称的 128B swizzle 不一致，它会把正确的字节当作错误位置的矩阵元素。先前 M2 的地址映射在这里接受真实 MMA 检验。

### 2.2 为何 `fence.proxy.async` 与 `__syncthreads()` 都要有

4.1 的生产者是普通线程 `st.shared`，消费者是 tcgen05 的异步读。它们属于不同 memory proxy。每个线程写完自己的 A/B 后执行：

```text
普通 SMEM store
→ fence.proxy.async.shared::cta
→ __syncthreads()
→ elected thread 发 MMA
```

- proxy fence：确保普通写对后面的异步代理可见；
- CTA 同步：确保所有 128 个线程都写完，而不只是发 MMA 的那个线程写完。

两者解决的是不同问题，不能互相替代。

### 2.3 为什么第一条 MMA 的累加位特殊

`tcgen05.mma` 的最后一个 predicate 相当于：

```text
false：D = A×B，不读取原有 TMEM D
true ：D = D + A×B
```

TMEM 刚分配时 D 不是已经初始化为0的普通数组。因此**整个 GEMM 只有第一条 MMA**，即 `(it=0, kk=0)`，要用 `false`：

```cpp
accumulate = (it != 0) || (kk != 0);
```

若写成 `kk != 0`，每轮 `kk=0` 都会清掉之前 K tile 的和。对于 `K=4096`，最后结果会丢掉前 63 个 `BK` tile。

### 2.4 为什么每轮都要等 `empty`

4.1 只有一份 A/B SMEM：

```text
MMA(it) 正从它读
下一轮线程想往同一地址写 A/B(it+1)
```

若直接写，就会覆盖 Tensor Core 尚在读取的输入。`tcgen05.commit` 只**登记完成通知**，并不是阻塞等待。因此每轮：

```text
发 4 条 MMA → commit 到 empty → wait empty[it&1] → 才能覆盖 SMEM
```

这里 `empty` 的语义是“Tensor Core 已消费完，本输入槽可以再写”。同一 barrier 对象在 K 循环中反复使用，等待 token 的 parity 是 `it&1`：`0,1,0,1...`。这正是 M3.3 常数 phase 错误在 M4 中的实际用途。

### 2.5 输出写回

TMEM 中一份 `128×64` f32 D，在 K 循环完成后才读取。四个 warp 各读 32 行；warp `w`、lane `l` 对应本地行 `w*32+l`。每次 `tcgen05.ld ... x8` 读 8 个连续列，`tcgen05.wait::ld` 后写入：

```cpp
gD[(tileM + row) * N + tileN + col + i] = r[i];
```

`tileM/tileN` 决定写到整个 D 的哪个 tile；`N` 是整张输出矩阵的行跨度。所有 warp 都读完后才 dealloc TMEM。

## 3. 4.2：用 TMA 替换手工搬运

### 3.1 TMA 改掉了什么，没改掉什么

4.1 每个元素大致经历：

```text
GMEM → 普通寄存器 → CUDA线程算索引和swizzle → st.shared → SMEM
```

4.2 改为：

```text
一个 elected thread 发两条 TMA copy
GMEM ────────────── TMA硬件（地址生成、搬运、swizzle） ─→ SMEM
```

**没变**：CTA 的输出 tile、每个 `BK` 的四条 MMA、同一份 TMEM accumulator、epilogue。

**也没自动解决**：单缓冲的拷贝与计算串行。SMEM 只有一份，计算没读完就不能搬下一份。

### 3.2 tensor map 是 TMA 的“快递单”

host 端为 A 和 B 分别调用 `cuTensorMapEncodeTiled`。tensor map 描述了大 tensor 的形状、外维 byte stride、一次要搬的 box、目标 SMEM swizzle。

| 参数 | A map | B map | 原因 |
|---|---|---|---|
| `globalDim` | `{K,M}` | `{K,N}` | dim0 是行内连续的 K |
| `globalStrides` | `{K*2}` | `{K*2}` | 跨一行走 `K` 个 bf16 |
| `boxDim` | `{BK,BM}` | `{BK,BN}` | 一次搬一个输入 tile |
| `elementStrides` | `{1,1}` | `{1,1}` | 不跳元素 |
| `interleave` | NONE | NONE | 行主序输入 |
| `swizzle` | 128B | 128B | 与 MMA descriptor 一致 |

TMA 坐标也按 `{K位置, 外维行}` 传：

```text
A：{it*BK, tileM}
B：{it*BK, tileN}
```

这和人常写的 `(row,col)` 顺序相反；把坐标颠倒是最容易出现“编译通过但算错”的问题。host 端现在检查两个 encode 的 `CUresult`，失败立即报错。

### 3.3 `full` 与 `empty` 是两张不同的“许可单”

```text
EMPTY ──TMA写入──> FILLING ──full完成──> FULL
  ▲                                      │
  │                                      MMA读取
  └──────────────empty完成────── CONSUMING
```

- `full`：TMA 已经把 A、B 两块都送到 SMEM，可以开始 MMA；
- `empty`：MMA 已经不再读取这份 A/B，可以被下一轮 TMA 覆盖。

单缓冲 K 循环的精确顺序：

```text
it=0：issue TMA0 → wait full0 → MMA0 → commit empty0
it=1：wait empty0 → issue TMA1 → wait full1 → MMA1 → commit empty1
it=2：wait empty1 → issue TMA2 → wait full2 → MMA2 → commit empty2
结束：wait 最后一轮 empty → 读 TMEM / 写 D
```

`issue TMA` 只是发出命令，`wait full` 才确认完成；`commit empty` 也只是登记通知，`wait empty` 才确认 MMA 消费完。

### 3.4 `expect_tx` 为什么填 24576

同一轮发两条 TMA：

```text
A：16 KiB = 16384 B
B： 8 KiB =  8192 B
总计         24576 B
```

两条 copy 共用 `full`，所以先调用一次 `mbarrier.arrive.expect_tx` 报总字节 `24576`。`full` 要等承诺的字节全部完成才翻相位。若只报 A 的字节数，可能在 B 还没到时提前允许 MMA 读取。

### 3.5 4.2 为什么删除 `fence.proxy.async`

4.1 是普通 `st.shared` → tcgen05 异步读，跨 generic/async proxy，需要显式 proxy fence。

4.2 是 TMA 异步写 → tcgen05 异步读，并由 `full` 报告 TMA 完成。这里不再需要 4.1 的 generic→async proxy fence。**但 `wait full`、`tcgen05.fence::after_thread_sync`、`wait empty`、TMEM `wait::ld` 都仍有不同作用，不能跟着删。**

## 4. 4.3：STAGES 级环形缓冲

### 4.1 stage、generation、parity 分别是什么

假设 `STAGES=3`，SMEM 有三个**物理槽**：

```text
stage0：[A 16KiB][B 8KiB]
stage1：[A 16KiB][B 8KiB]
stage2：[A 16KiB][B 8KiB]
```

逻辑 K tile 编号 `it` 不断增加，但物理槽循环复用：

```cpp
stage      = it % STAGES;
generation = it / STAGES;   // 整数除法：该槽第几次使用
parity     = generation & 1; // mbarrier 在该槽的奇偶 phase
```

| `it` | 槽 `it%3` | 槽的使用轮 `it/3` | 该轮 `full` parity |
|---:|---:|---:|---:|
| 0 | 0 | 0 | 0 |
| 1 | 1 | 0 | 0 |
| 2 | 2 | 0 | 0 |
| 3 | 0 | 1 | 1 |
| 4 | 1 | 1 | 1 |
| 5 | 2 | 1 | 1 |
| 6 | 0 | 2 | 0 |

类比：`stage` 是哪个盘子；`generation` 是这个盘子第几次装菜；`parity` 是盘子旁边每轮翻一次的两面卡片。**parity 是针对同一个 barrier 地址的复用轮次，不是 `it&1`。**当 `S=3` 时，tile3 回到 stage0 才把 stage0 的 phase 从0变1。

每个 stage 有独立 `full[s]` 和 `empty[s]`。因为 stage0 可能已空，stage1 可能仍在被读；一个全局 barrier 无法同时表达两者状态。

### 4.2 写入前的 token 与读取前的 token

准备给逻辑 tile `j` 发 TMA：

```cpp
s = j % STAGES;
gen = j / STAGES;
```

若 `gen==0`，该 stage 第一次使用，天然为空，无须等 `empty`。

若 `gen>0`，必须等**上一次使用这个 stage**的 MMA 完成：

```cpp
wait empty[s], token = (gen-1)&1;
```

TMA 发出后，真正使用这块数据前等待**本 generation** 的 `full`：

```cpp
wait full[s], token = gen&1;
```

例如 stage0：

```text
tile0/gen0：第一次写，不等 empty → TMA0 → wait full token0 → MMA0 → empty token0完成
tile3/gen1：先 wait empty token0 → TMA3 → wait full token1 → MMA3 → empty token1完成
tile6/gen2：先 wait empty token1 → TMA6 → wait full token0 → MMA6
```

`try_wait.parity` 的 token 是“正在等待哪一轮完成”，不是“希望 barrier 当前显示哪个 parity”。

### 4.3 三个时间阶段：Prime / Steady / Drain

它们是**运行时间阶段**，不是三个物理 stage。

**Prime（预热）**：先发 `min(STAGES, K/BK)` 个 TMA，尽量让输入槽先填起来。此时还没开始前一块 MMA，因此启动空泡不可避免。

**Steady（稳态）**：计算当前 K tile 时，尝试把未来 K tile 发到已释放的 stage。TMA 写未来 stage，Tensor Core 读当前 stage，可在不同硬件路径上重叠。

**Drain（排空）**：最后一轮 MMA commit 后，没有下一次循环替我们等它；必须 `wait empty[last]`，确认 TMEM D 完整，再 epilogue。

```text
时间 ─────────────────────────────────────────────────────────▶
stage0：TMA0 ─ FULL0 ─ MMA0 ─ EMPTY0 ─ TMA3 ─ FULL3 ─ MMA3
stage1：  TMA1 ─ FULL1 ────── MMA1 ─ EMPTY1 ─ TMA4
stage2：    TMA2 ─ FULL2 ──────── MMA2 ─ EMPTY2 ─ TMA5
          └──── prime ────┘ └──────── steady ───────┘ drain
```

这张图表达**可重叠关系**，不按真实周期比例。不能让 `TMA1` 与 `MMA1` 同时读写 stage1；可以让 `TMA3` 写 stage0 的同时，`MMA1` 读 stage1。

### 4.4 `next_issue`：为何“机会预取”还需要“强制发射”

源码中的 `next_issue` 是**下一块尚未发出 TMA 的逻辑 tile 编号**。不变量：

```text
所有 j < next_issue：TMA 已发出，且恰好一次
所有 j ≥ next_issue：还没有发出
```

Prime 后，`S=3` 时 `next_issue=3`。若 stage0 尚未被 MMA0 读完：

```text
try empty[0] 失败
→ 暂时不发 TMA3
→ next_issue 仍是 3（绝不能加到4）
```

之后主循环真的来到 `it=3`，必须先检查：

```text
next_issue <= it ?
是 → 阻塞等 stage0 empty → 确实发出 TMA3 → next_issue++
然后才能 wait full[0] 等 TMA3 完成
```

如果先前 `try` 失败，却错误地认为 tile3 已发，到了 `it=3` 直接等 `full3`，就会**等一条从未发出的拷贝**，kernel 死锁。

```text
机会式预取：stage 暂未空 → 不等，继续计算；它负责“快”。
强制发射：当前必需 tile 尚未发 → 必须等空并发出；它负责“活”。
```

实现用单个 elected thread 串行维护 `next_issue`，不需要为每个 tile 开一个共享标志。`issue_tile()` 先对当前 stage 的 `full` 执行 `arrive.expect_tx`，再发 A/B 两条 TMA。

### 4.5 为什么还等“前一个 MMA”的 empty

所有 K tile 都累加到**同一份 TMEM D**。代码在发本轮 MMA 前，保守地等待上一轮 `empty`：

```text
预取未来 TMA
→ wait 当前 full
→ wait 前一轮 MMA empty
→ 发当前四条 MMA
```

这明确完成了同一 accumulator 的累加依赖。它会限制同时在途的 MMA 组数，但不抹掉核心收益：**未来 tile 的 TMA 已经发出，仍可与前一轮或本轮的 Tensor Core 工作重叠**。这是为了正确性与可读性选择的保守调度；若 B300 实测显示等待成为瓶颈，可在确认 tcgen05 指令顺序与同步语义后再优化，不能无证明地删掉。

### 4.6 stage 数为什么不是越多越好

| STAGES | 输入 SMEM | 加最多 1024 B 对齐余量的申请量 |
|---:|---:|---:|
| 2 | 48 KiB | 49 KiB |
| 3 | 72 KiB | 73 KiB |
| 4 | 96 KiB | 97 KiB |
| 6 | 144 KiB | 145 KiB |

更多 stage 可以更早发 TMA、增加 in-flight 请求、隐藏延迟；但每个 CTA 的 SMEM 线性增长，可能让一个 SM 同时驻留的 CTA 更少，降低另一种延迟隐藏来源——CTA/warp 并发。TMEM accumulator 不随 stage 数增加，仍是 32 KiB。

对 `4096³`，grid 有 2048 CTA、每 CTA 64 轮 K；对 `256×4096×16384`，只有 128 CTA、每 CTA 256 轮 K。后者 CTA 间并发较弱、稳态较长，理论上对 CTA 内 pipeline 深度更敏感；**哪个 S 实际最佳要以 B300 sweep 为准**。

## 5. 几个容易犯错的对照

| 错法 | 后果 | 正确想法 |
|---|---|
| 每轮 `kk=0` 都关闭累加 | 以前的 K tile 部分和被覆盖 | 只在 `(it,kk)=(0,0)` 关闭 |
| 4.1 写完 SMEM 只做 `__syncthreads()` | generic/async proxy 可见性未建立 | 每线程 proxy fence，再 CTA sync |
| TMA 坐标传 `{tileM,it*BK}` | tensor map dim0/1 颠倒 | `{it*BK,tileM}` |
| `expect_tx` 只报 A 字节 | `full` 可能不覆盖 B 的完成 | 报 A+B 总 24576 B |
| 见到 `issue TMA` 就开始 MMA | TMA 还可能在搬 | 先等本轮 `full` |
| MMA commit 后立即覆盖 stage | commit 不等于完成 | 等上一代 `empty` |
| 4.3 使用 `it&1` 作所有 stage 的 parity | 同一 stage 的相位节奏错 | `(it/STAGES)&1` |
| `try empty` 失败后递增 `next_issue` | 当前 tile 永远没发，`wait full` 死锁 | 发出后才递增，消费前 force issue |
| 最后一个 MMA 后直接读 TMEM | 读到未完成部分和 | Drain 等最后 `empty` |

```text
等 EMPTY（槽可覆写）

→ 等 EMPTY（计算已消费完槽）
```
